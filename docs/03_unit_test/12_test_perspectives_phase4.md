## 前提：TypeScript/Svelte側テストの勘所（フェーズ1〜3との違い）

`01_test_plan.md` 4章・5章より、フェーズ4はテストランナーが**Vitest**、コンポーネントテストは**`@testing-library/svelte`**、`localStorage`等ブラウザAPIは**`vi.stubGlobal` / jsdom環境**でモック化する方針ですわ。Go＋testifyのテーブル駆動テストとは前提が変わるため、フェーズ1〜3で積み上げてきた「純粋ロジックはモック不要で軽量にテストする」という思想を、**Svelteコンポーネントの世界でどう再現するか**が本フェーズの最大の論点になりますの。

1. **Svelteの`$:`リアクティブ宣言・`export let`直下に判定ロジックを直接書かないこと。** テスト計画書4章にも「ロジックのみを切り出せる部分は、コンポーネントから独立した純粋関数としてユニットテストする」と明記されている通り、disabled判定・モード判定・エラー出し分けといった分岐は、コンポーネントの外に置いた純粋関数（例：`isSendButtonDisabled(...)`）として抽出し、コンポーネント側はその戻り値をバインドするだけの薄い層にすべき。これが徹底されていないと、1つの分岐をテストするためだけに毎回コンポーネント全体をマウントする必要が生じ、F.I.R.S.T原則の「Fast」に反する。
2. **`localStorage`のような副作用を伴うブラウザAPIは、コンポーネントから直接呼ばず、薄いラッパー関数（例：`getStoredInputMode()` / `setStoredInputMode()`）越しに呼ぶこと。** ラッパー関数自体は`vi.stubGlobal('localStorage', ...)`でモック化した`Storage`相当のオブジェクトを注入してテストし、コンポーネント側は「ラッパー関数が正しい引数で呼ばれたか」だけを検証する、という2層構成が望ましい。
3. **時刻・タイマーに依存する処理（4-3のトースト3秒消滅）は`vi.useFakeTimers()`を用いること。** `.claude/rules/tdd-comprehensive.md`の「実際の時間に依存しない」原則そのままで、実際に3秒待つテストは書かない。
4. **コンポーネントテストは「実装の詳細」ではなく「ユーザーから見た振る舞い（DOM・ロール）」を検証すること。** `screen.getByRole('button', { name: '送信' })`のように、内部state名やクラス名に依存しない検証を徹底する（`ts-svelte-coding-guideline.md`のテスト方針とも整合）。

各機能の「責務分離の指摘」で、この4点に沿った具体的な切り出し方を提案しますわね。

## 4-1. 入力モード切替（マイク/テキスト）とlocalStorage保存

**根拠**: 画面設計書「モード状態の永続化」（320〜328行目付近）

### 正常系

- 初期表示時、`localStorage`に`zuncha_input_mode`キーが存在しない場合、モードは初期値`"voice"`になる。
- モード切替トグルの「テキスト」を選択すると、内部状態が`"text"`に切り替わり、`localStorage`の`zuncha_input_mode`に`"text"`が保存される。
- 「マイク」を選択すると`"voice"`に戻り、`localStorage`にも`"voice"`が保存される。
- コンポーネントの再マウント（ページ再読み込み相当）時、`localStorage`に既存の値（例：`"text"`）が保存されていれば、初期値としてその値が採用される（初期値`"voice"`より`localStorage`の値が優先される）。

### 異常系

- **【7章T確定】** `localStorage`に`zuncha_input_mode`以外の想定外の値（例：`"foo"`、`"1"`、空文字列）が保存されている場合、無効値として扱い**デフォルト`"voice"`にフォールバックする**。
- **【7章T確定】** `localStorage.getItem` / `setItem`自体が例外を投げる場合（プライベートブラウジングでのQuotaExceededError、SecurityError等）も、例外を握って**デフォルト`"voice"`にフォールバックする**（クラッシュさせない）。

### 境界値

- **【7章T確定】** `localStorage`の値が仕様上の2値（`"voice"` / `"text"`）と大文字小文字だけ異なる場合（例：`"Voice"`）は、**正規化せず無効値として扱い、デフォルト`"voice"`にフォールバックする**（フェーズ1確認事項Cの厳密一致方針を踏襲）。
- モード切替を高速に連続操作（マイク→テキスト→マイク→テキスト…）した場合、最終的な`localStorage`の値が最後の操作と一致すること（中間状態の値が誤って残らないか）。

### 例外系（★フェーズ4特有・最重要論点）

- **【7章U確定】** 録音中・STT変換中は、モード切替トグル自体を**disabled化**する。誤ってモードを切り替えられてしまうことによる、録音中のマイクストリームや変換中のSTT処理との競合を防ぐ。
- **【7章U確定】** モード切替時、旧モードのテキスト入力欄の文字列は**クリアする**（保持しない）。保持すると、テキストモードに残った文字列が音声モードに切り替えた後も残存し、次にテキストモードへ戻した際に意図せず送信可能状態になる副作用があるため。

### 責務分離の指摘

- **`localStorage`の読み書きは`getStoredInputMode(): InputMode` / `setStoredInputMode(mode: InputMode): void`のような純粋関数（副作用は`localStorage`呼び出しのみ）に切り出すこと。** Segmented Controlコンポーネント自体は、この関数を呼ぶだけの薄い層にする。こうすることで、「不正値が保存されていた場合のフォールバック」のような分岐は、コンポーネントをマウントせずに関数単体でテストできる。
- **モードの型は`type InputMode = 'voice' | 'text'`のようなUnion型として定義し、文字列リテラルを直接あちこちに書き散らさないこと。** `ts-svelte-coding-guideline.md`の「ユニオン型には型エイリアスを使用する」に従う。不正値のバリデーションも、この型に対する型ガード関数（`isInputMode(value: unknown): value is InputMode`）として実装すれば、4-1のロジックはモック不要な純粋関数としてテストできる部分（型ガード）と、`localStorage`アクセスが絡む部分（読み書きラッパー）に自然に分離される。
- **Svelteコンポーネント単体テストの切り出し方**：本機能については、①「トグルをクリックすると対応するコールバックが呼ばれる」というコンポーネントレベルのテスト（`@testing-library/svelte`でクリックイベントを発火し、表示されるアクティブスタイル・ラベルを検証）と、②「`localStorage`の読み書き・不正値のフォールバック」という純粋関数レベルのテストを分けて設計すべき。①は少数（正常系のクリック挙動のみ）に絞り、②で異常系・境界値を厚く網羅する方が、テストピラミッドの比率（Unit多め・コンポーネントテスト少なめ）にも合致する。
- **【7章T確定】** `isInputMode`型ガードが`false`を返すケース（無効値）は、呼び出し元で必ず`"voice"`へのフォールバックを行う設計とする。フォールバック処理自体もこの型ガードと同じ純粋関数側に閉じ込め、コンポーネント側で個別に分岐しないようにする。
- **【7章Z確定】** `localStorage`のモックは`vi.stubGlobal('localStorage', ...)`で独自の`Storage`モックオブジェクトに完全に置き換える方針とする。`getStoredInputMode`/`setStoredInputMode`の呼び出し引数（キー・値）をスパイ的に検証しやすくするため。

## 4-2. 送信ボタンの活性制御

**根拠**: 画面設計書8章（339〜349行目、434〜441行目付近）

### 正常系

- 音声モードで録音完了後（音声データあり）、送信ボタンは有効化される（`disabled = false`）。
- テキストモードで、空でない通常の文字列（例：`"こんにちは"`）が入力欄にある場合、送信ボタンは有効（`disabled = false`）。
- テキストモードで、STT成功による自動入力後（画面設計書「編集可能（テキスト反映）」状態）、反映された文字列が空でなければ送信ボタンは有効になる。

### 異常系

- 音声モードで、録音前（待機中、まだ録音していない）の場合、送信ボタンは無効（`disabled = true`）（画面設計書339〜349行目の表に明記）。
- テキストモードで、入力欄が空文字列（`""`）の場合、送信ボタンは無効。
- テキストモードで、入力欄が空白のみ（半角スペース・タブ・改行・全角スペース`　`等、trim後に空になる文字列）の場合、送信ボタンは無効。
- テキストモードで、STT変換中（readonly状態）の場合、入力欄の内容に関わらず送信ボタンは無効。
- **【7章V確定】** 音声モードで「録音中」（録音開始後・停止前）の場合も、送信ボタンは無効（`disabled = true`）。有効化されるのは録音完了後（音声データ確定後）のみ。
- **【7章W確定】** 送信ボタン押下後、SSE `done`イベント受信までの間（送信中）は、モード・入力内容に関わらず送信ボタンは無効（二重送信防止）。

### 境界値

- テキストモードで、入力が1文字のみ（例：`"あ"`）の場合、送信ボタンは有効（「空でない」ことの最小境界）。
- trim対象文字種の網羅：半角スペースのみ／タブのみ／改行のみ／全角スペース（`　`）のみ／これらの混在、いずれも空扱いとなり無効化されること（JS標準の`String.prototype.trim()`が`　`を含む点を明示的にテストケース化する）。
- 非常に長い文字列（例：1,000文字）が入力欄にある場合でも、文字数上限による無効化は発生しない（画面設計書に文字数上限の明記がないため、上限なしを仕様として確認する意味を含む）。

### 例外系（★フェーズ4特有・最重要論点）

- **【7章V確定】** 音声モードの送信ボタンは「録音完了前は全てdisabled」を正式仕様とする。画面設計書339〜349行目の「録音前のみdisabled」という表記は簡略化と解釈し、録音中も含めて未確定データでの送信を防ぐ。
- **【7章W確定】** 送信中（クリック後〜SSE `done`受信まで）もdisabled化する。画面設計書の記載漏れと判断し、`tdd-comprehensive.md`のエッジケース・カタログにある「連続操作・二重送信」の典型パターンとして、安全側の仕様として確定。
- テキストモードで、STT失敗時（画面設計書9-1「編集可能（空・手動入力可能）」）に戻った直後は入力欄が空のはずなので送信ボタンは無効となるが、**この状態遷移が4-1のモード切替・4-3のエラー表現と同時に発生した場合に、3つの状態管理が競合しないか**（機能間の結合点として要注意。この点は今回の仕様決定の対象外として残る）。

### 責務分離の指摘

- **disabled判定は`isSendButtonDisabled(params: { mode: InputMode; text: string; isRecording: boolean; isTranscribing: boolean; hasRecordedAudio: boolean }): boolean`のような単一の純粋関数に集約すること。** モード・入力文字列・録音中フラグ・変換中フラグ・録音済みフラグという複数の状態の組み合わせ判定を、コンポーネントの`$:`宣言内に直接書くと、`tdd-comprehensive.md`が警告する「矛盾する状態の組み合わせ」のテストのたびにコンポーネント全体をマウントする必要が生じる。純粋関数化すればテーブル駆動的なテスト（Vitestの`describe.each`）で高速に網羅できる。
- **テキストモードの空白判定（trim後空か）は、1-4（Go側）で確立した「空文字・空白のみのtrim判定」と判定基準を一致させること。** 実装言語（Go/TypeScript）が異なるため関数自体は共有できないが、「どの文字種を空白とみなすか」という**仕様レベルの一致**は保つべきで、1-4のテストケースをTS側のエッジケース設計の参考にする。
- **録音中・変換中・編集可能・送信中といった一連の状態は、個別のbooleanフラグの組み合わせで表現するのではなく、`type InputState = 'idle' | 'recording' | 'transcribing' | 'editable' | 'sending'`のような単一の状態機械（Union型）で表現すること。** booleanの組み合わせで表現すると「録音中かつ変換中」のような本来あり得ない矛盾状態が型レベルで表現可能になってしまい、テストケースも本来不要な組み合わせまでカバーする必要が生じる。状態機械化すれば、`isSendButtonDisabled`は「この状態のとき無効か」という単純なswitch/mapになり、テストの見通しが良くなる。
- **【7章V・W確定】** `InputState`には録音中（`recording`）・送信中（`sending`）を明確に含め、`isSendButtonDisabled`はこの2状態も無効化対象として扱う設計にすること。

## 4-3. エラー表現の出し分け（ずんだもん応答バブル vs 3秒トースト）

**根拠**: F-STT-02, F-STT-03 / 画面設計書9章（469行目、475〜477行目、496〜551行目）

### 4-3のスコープに関する前提整理（★ユーザー指摘の核心）

画面設計書9-3・フェーズ3の確認事項K・L・M・N（`09_test_perspectives_phase3.md` 7章）により、**エラー種別ごとの出し分けはすでにバックエンド側で確定済み**ですわ。

- STT認識失敗（F-STT-02）・STTタイムアウト（F-STT-03）→ 通常の`text`/`emotion`イベント（感情`困惑`＋リトライ文言）として送出。**フロントから見れば「普通の応答」と同じSSEイベント種別**であり、特別な"エラー"イベントではない。
- システム/通信エラー・LLMパース失敗・STT以外のバックエンドエラー（フェーズ3の確認事項K）→ SSE `error`イベントとして送出。

つまり、**フロントエンド側には「このエラーはバブルかトーストか」を判定する独自ロジックは存在せず、SSEイベント種別（`text`/`emotion` か `error` か）に応じたハンドラのルーティングに過ぎない可能性が高い**ですの。この前提が正しいかどうかで4-3のテスト設計は大きく変わるため、[確認事項X](#6-横断的な指摘事項つむぎ確認事項)として提起していましたが、**【7章X確定】単純ルーティングという理解で正しいことが確定し、フロントに判定ロジックは実装しない**ことが決まりましたわ。以下の観点はこの確定を前提としていますの。なお、F-RT-02（SSE自動再接続）時のUI表現は画面設計書に明記がなく、**本フェーズのスコープ外**として将来別途対応することも確定していますわ。

### 正常系

- SSE `error`イベントを受信すると、ペイロードの`message`をテキストとしたエラートーストが表示される。
- SSE `error`イベント受信から3秒後、トーストがDOMから自動的に消滅する。
- SSE `text`/`emotion`イベント（困惑・リトライ文言を含む場合も同様）を受信すると、既存の応答表示ロジックと同一パスで、会話ログにずんだもん応答バブルとして追記される（**STT失敗由来かどうかを判定する特別分岐が存在しないこと**も仕様として確認する）。

### 異常系

- `error`イベントのペイロードに`message`フィールドが欠落・空文字列の場合の表示内容（デフォルトメッセージへのフォールバックが必要か未定義→確認事項Y寄り）。
- トースト表示中（3秒タイマー作動中）に、コンポーネントがアンマウントされた（画面遷移等）場合、タイマーが正しくクリアされ、アンマウント後に状態更新エラー（Svelteの「destroyed componentへの書き込み」警告等）が発生しないこと。

### 境界値

- トースト表示から2,999msの時点ではDOMに存在し、3,000msの時点で消滅していること（`vi.useFakeTimers()` + `vi.advanceTimersByTime()`で厳密に検証）。
- `error`イベントが短時間（例：100ms間隔）で連続して複数回届いた場合のトースト表示の挙動（1件目のトーストが消える前に2件目が届いた場合、上書き・キューイング・多重表示のいずれかになるが、画面設計書に明記なし）。

### 例外系（★フェーズ4特有・最重要論点）

- **【7章X確定】** 4-3の「出し分け」はSSEイベント種別のルーティングに過ぎず、フロント側に独自の判定ロジックは実装しない。フェーズ4-3の実質的なテスト対象は「イベントハンドラのルーティング（`error`→トースト表示関数呼び出し、`text`/`emotion`→ログ追記関数呼び出し）」に確定する。
- **【7章X確定】** F-RT-02（SSE自動再接続）時のUI表現は本フェーズのスコープ外とする（画面設計書・要件定義書に明記がなく、将来別途対応）。
- **【7章Y確定】** 本フェーズのユニットテスト対象は「①イベントルーティング関数」と「②Toastコンポーネントの3秒消滅・応答バブルとの共通パス検証」の**両方**とする。ただし色・フォント等の視覚仕様（CSS具体値）の検証は対象外とし、DOM構造・ロール・表示テキスト・タイマー挙動に絞る。

### 責務分離の指摘

- **【7章X・Y確定】** 「SSEイベント受信→表示すべきUI要素の決定」という薄いルーティング層と、「トースト・応答バブルの実際の描画・タイマー管理」という表示層を分離すること。前者は`routeSSEEvent(event: SSEEvent): void`のような関数として、イベント種別ごとに対応するstore更新・関数呼び出しを行うだけの薄い実装にし、モック化したイベントを渡して呼び出し先が正しいかだけを検証する（例：`error`イベントを渡すと`showToast`相当のstore更新関数が呼ばれたことを検証）。後者（Toastコンポーネント自体）は`@testing-library/svelte`でマウントし、propsとして渡されたメッセージが表示され、3秒後に消えることを検証する、という2層のテストに分ける。
- **トーストの3秒自動消滅は`setTimeout`依存のため、`vi.useFakeTimers()`を用いて決定的にテストすること。** 実際に3秒待つテストを書くと、`tdd-comprehensive.md`が禁止する「実際の時間に依存するテスト」に該当し、CI実行時間の肥大化・フレーキーテスト化を招く。
- **応答バブル側は「困惑」感情＋リトライ文言のケースも、通常の応答と全く同じコンポーネント・同じ関数パスで表示されることをテストで固定すべき。** これは「STT失敗かどうかで表示分岐している実装になっていないか」を検知するネガティブテストとしての価値があり、前提整理で述べた「フロントに判定ロジックは存在しないはず」という設計意図をテストコードとして明文化する意味を持つ。

## 総括：フェーズ4に共通するテスト容易性の論点

フェーズ1〜3はいずれもGo側の「純粋関数として切り出せるか」「モックの粒度をどこに置くか」が焦点でしたが、フェーズ4はSvelteという**UIフレームワーク特有の結合**が新たな論点として加わりますわ。3機能に共通する望ましい設計は次の通りですの。

1. **判定・状態管理ロジックは、コンポーネントの`$:`宣言や`export let`直下ではなく、独立した純粋関数・Union型として切り出すこと。** 4-1のモード判定、4-2のdisabled判定、4-3のイベントルーティングは、いずれもコンポーネントをマウントせずに単体でテストできる設計が可能であり、そうすべき。フェーズ1で確立した「純粋ロジックは軽量にテストする」という利点は、TypeScript/Svelte側でも同じ思想で再現できる。
2. **ブラウザAPI（`localStorage`）・タイマー（`setTimeout`）といった副作用は、薄いラッパー関数越しに呼び、テストでは`vi.stubGlobal`・`vi.useFakeTimers`で決定的に制御すること。** テスト計画書5章の方針そのものであり、実装時にもこの粒度が徹底されているか確認が必要。
3. **状態はbooleanフラグの組み合わせではなく、Union型による状態機械として表現すること。** 4-2の録音中/変換中/編集可能/送信中、4-1のvoice/textはいずれも「本来あり得ない矛盾状態」を型レベルで排除できる設計にすべきで、こうすることでテストケースの組み合わせ爆発を防げる。
4. **フェーズ3との境界（4-3）は、バックエンド側で既に決着した設計判断（フェーズ3確認事項K・L・M・N）を前提にすると、フロント側の実質的なテスト対象が小さくなる可能性が高い。** この前提の正誤（確認事項X）が本フェーズの作業量そのものを左右するため、他の確認事項（T・U・V・W・Z）より優先してつむぎの判断を仰ぐべきですわ。

6章の確認事項T〜Zは、次工程（ひまりのテストケース設計）に進む前に解消が望ましいですの。特にXは4-3全体のスコープを規定するため優先度が高いと考えますわ。

**2026-07-09追記**: 6章の確認事項T〜Zはつむぎの決定（[7章](#7-つむぎによる仕様決定)参照）により全て解消済みですわ。4-1〜4-3の該当箇所も確定版に更新済みなので、ひまりへのテストケース設計、このまま進めてもらって大丈夫ですの。

## 7. つむぎによる仕様決定

6章で提起された確認事項T〜Zについて、つむぎが2026-07-09時点で決定した内容を記録する。ひまりのテストケース設計は本決定を前提として進めてよい。

### T. 4-1のlocalStorage不正値・例外時のフォールバックについて

- **決定**: 想定外の値（`"voice"`/`"text"`以外、大文字小文字違いの`"Voice"`等も含む）、および`getItem`/`setItem`が例外を投げる場合は、いずれもデフォルト`"voice"`にフォールバックする（例外は握ってクラッシュさせない）。大文字小文字の正規化は行わない（無効値として扱う）。
- **理由**: フェーズ3確認事項Lと同じ思想。ブラウザAPI・永続化データは完全制御できない外部要因であり、エラーで機能を止めるとUXが損なわれる。正規化しない点はフェーズ1確認事項C（ULID完全一致、正規化なし）の厳密一致方針を踏襲する。
- **4-1への影響**: 異常系・境界値のテストケースの期待値は「無効値・例外いずれのケースでもデフォルト`"voice"`にフォールバックする」ことの検証に確定する。

### U. 4-1の録音中・STT変換中のモード切替可否について

- **決定**: モード切替トグル自体をdisabled化する。切替時、旧モードのテキスト入力欄の文字列はクリアする（保持しない）。
- **理由**: 進行中の処理と状態が競合するリスクを避ける。4-2の「処理中はdisabled」という設計思想と一貫させる。保持すると意図しない送信可能状態を生む副作用があるため。
- **4-1への影響**: 例外系のテストケースは「録音中・変換中はトグルがdisabledになる」「モード切替時に旧モードの入力がクリアされる」の2点を検証する形に確定する。

### V. 4-2の録音中の送信ボタン活性について

- **決定**: 「録音中」も disabled とする。有効化は「録音完了後（停止後・音声データ確定後）」のみ。
- **理由**: 未確定データでの送信を防ぐため。画面設計書の「録音前のみdisabled」という表記は簡略化と解釈し、「録音完了前は全disabled」を正式仕様とする。
- **4-2への影響**: 異常系・例外系のテストケースの期待値は「録音完了前（待機中・録音中いずれも）はdisabled、録音完了後のみ有効」に確定する。

### W. 4-2の送信中のdisabled化について

- **決定**: クリック後〜SSE `done`受信までの間はdisabled化する（二重送信防止）。
- **理由**: `tdd-comprehensive.md`が明示する典型的エッジケース。画面設計書の記載漏れと判断し、安全側の仕様として確定する。
- **4-2への影響**: 異常系・例外系のテストケースに「送信中はモード・入力内容に関わらずdisabled」を追加する。`InputState`の状態機械に`sending`を含めることが前提となる。

### X. 4-3のエラー出し分けはフロント独自ロジックか単純ルーティングかについて

- **決定**: 単純ルーティングという理解で正しい。フロントに判定ロジックは実装しない。なお、F-RT-02（自動再接続）のUI表現は画面設計書に明記がなく、本フェーズのスコープ外とする（将来別途対応）。
- **理由**: フェーズ3確認事項K・M・Nでバックエンド側が既に振り分け済み。フロントでの再判定は責務重複になる。
- **4-3への影響**: 4-3の実質的なテスト対象は「イベントハンドラのルーティング」に確定し、判定ロジック自体のテストケースは不要になる。F-RT-02関連のテストケースも本フェーズには含めない。

### Y. 4-3のテスト対象範囲（判定ロジックのみか表示コンポーネントまでか）について

- **決定**: 両方対象とする。①イベントルーティング関数（純粋関数）と②Toastコンポーネントの3秒消滅・応答バブルとの共通パス検証（`@testing-library/svelte`＋`vi.useFakeTimers`）の2階層。ただし色・フォント等の視覚仕様（CSS具体値）の検証は対象外とし、DOM構造・ロール・表示テキスト・タイマー挙動に絞る。
- **理由**: テストピラミッドの両層を適切にカバーする。デザイントークンの数値検証は`01_test_plan.md`2章のスコープ外事項（ビジュアルリグレッションの範疇）と整合させる。
- **4-3への影響**: テストケース設計は「①ルーティング関数の単体テスト」と「②Toast/応答バブルコンポーネントの振る舞いテスト」の2系統に分けて作成する。

### Z. 4-1のlocalStorageモック方針について

- **決定**: `vi.stubGlobal`で独自の`Storage`モックオブジェクトに完全に置き換える。
- **理由**: ラッパー関数のスパイ的検証（正しいキー・値で呼ばれたか）や、確認事項Tの例外注入テストを実現しやすいため。
- **4-1への影響**: テストコードは`vi.stubGlobal('localStorage', mockStorage)`のパターンに統一する。jsdom標準実装への依存は行わない。
