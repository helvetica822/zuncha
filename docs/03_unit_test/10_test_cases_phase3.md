## 3-1. `ParseLLMResponse`（パース層。純粋関数、モック不要）

**対象関数**: `ParseLLMResponse(body []byte) (*LLMResponse, error)`。LLM呼び出し（HTTPクライアント）から完全に分離し、レスポンスボディを受け取ってstructまたはエラーを返す純粋関数として設計する。`emotion`の妥当性検証は1-3の`ValidateEmotion`を再利用し、7種外の場合は確認事項Lにより`困惑`へフォールバックする。エラーは「構文エラー」「スキーマ検証エラー」「値検証エラー」の3種別に区別できる設計とする。Markdownコードブロック除去はこの関数の責務に含めない（7章Q参照）。

## 3-2. SSEイベント送出ロジック（オーケストレーション層。モック必須）

**対象関数**: `StreamResponse(sink EventSink, llmClient LLMClient, ttsClient TTSClient, ...) error`相当のオーケストレーション関数。`LLMClient`・`TTSClient`・`EventSink`（送出イベントの種別・ペイロード・順序を記録するテスト用シンク）をすべてモック化して検証する。実際のSSEストリーム（`http.ResponseWriter`）は用いない。

### 正常系

| ID | Given（前提条件） | When（操作） | Then（期待結果） |
|----|-------------------|-------------|------------------|
| TC-3-2-01 | `LLMClient`・`TTSClient`のモックが両方成功を返すよう設定する | `StreamResponse(...)`を呼ぶ | `emotion`→`text`→`audio_url`→`done`の順で送出される（確認事項M） |
| TC-3-2-02 | `text`が3チャンクに分割して送出される設定にする | `StreamResponse(...)`を呼ぶ | 3チャンクすべてが`done`より前に送出完了している |
| TC-3-2-03 | 正常応答フローを実行する | 各イベントのペイロードを検証する | `emotion`は`{"label": "喜び"}`、`text`は`{"chunk": "..."}`、`audio_url`は`{"url": "/audio/{ulid}"}`の形式である |
| TC-3-2-04 | `text`が1チャンクのみで完結する設定にする | `StreamResponse(...)`を呼ぶ | `text`→`done`の順で正しく送出される |
| TC-3-2-05 | `text`が100チャンクに分割される設定にする | `StreamResponse(...)`を呼ぶ | 全100チャンクが送出した順序通りにシンクへ記録される（順序の入れ替わりがない） |

### 異常系

| ID | Given（前提条件） | When（操作） | Then（期待結果） |
|----|-------------------|-------------|------------------|
| TC-3-2-06 | `LLMClient`モックがエラーを返すよう設定する（確認事項K） | `StreamResponse(...)`を呼ぶ | `text`/`emotion`イベントは送出されず、`error`イベントのみが送出される |
| TC-3-2-07 | `LLMClient`は成功、`TTSClient`モックがエラーを返すよう設定する（確認事項N） | `StreamResponse(...)`を呼ぶ | `audio_url`は送出されず、`emotion`・`text`は送出済みのまま`done`が送出される（`error`にはしない） |
| TC-3-2-08 | `ParseLLMResponse`が返す`emotion`値が不正な状態（本来到達しない想定）を意図的に注入する | `StreamResponse(...)`を呼ぶ | エラーとして扱われ、`emotion`イベントは送出されない（7章S参照） |

### 例外系（送出順序・状態遷移の契約）

| ID | Given（前提条件） | When（操作） | Then（期待結果） |
|----|-------------------|-------------|------------------|
| TC-3-2-09 | 正常応答フローを実行する | 送出されたイベント列を検証する | `emotion`が`text`より必ず先に送出される（確認事項M） |
| TC-3-2-10 | `text`が複数チャンクに分割される正常応答フローを実行する | 送出されたイベント列を検証する | 全`text`チャンクの送出完了後でなければ`audio_url`は送出されない |
| TC-3-2-11 | 正常応答フロー、およびTTS失敗フローの両方を実行する | 送出されたイベント列を検証する | いずれのフローでも`audio_url`（または省略）の後でなければ`done`は送出されない |
| TC-3-2-12 | `text`送出中に`EventSink`の`SendTextChunk`が書き込み失敗を返す設定にする | `StreamResponse(...)`を呼ぶ | `error`イベントが送出中の任意のタイミングで割り込んで送出できる（確認事項M） |
| TC-3-2-13 | `error`が送出される条件（確認事項K）を設定する | `StreamResponse(...)`を呼ぶ | `error`送出後、`text`/`emotion`/`audio_url`/`done`のいずれも送出されない |
| TC-3-2-14 | 正常応答フローを実行する | `done`イベントの送出回数を数える | `done`はちょうど1回だけ送出される（重複送出なし） |
| TC-3-2-15 | 正常応答フロー・TTS失敗フロー・LLM失敗フローをそれぞれ実行する | 各フローの最終イベントを確認する | いずれのフローでも`done`または`error`のどちらかで必ず終端する（ハングしない） |

## 3-3. `IsRecognitionFailed`／`IsTimedOut`（判定層。純粋関数、モック不要）

めたんの指摘に基づき、2つの完全に独立した純粋関数として設計する。困惑メッセージ・感情ラベルへのマッピングは3-3のスコープ外（3-2または上位オーケストレーション層の責務）とし、本書では扱わない。

### 3-3-1. `IsRecognitionFailed(result STTResult) bool`

| ID | Given | When | Then |
|----|-------|------|------|
| TC-3-3-R01 | `result.Text = "こんにちは"`, `result.Confidence = 0.8`（閾値以上） | `IsRecognitionFailed(result)`を呼ぶ | `false`を返す |
| TC-3-3-R02 | `result.Text = ""`（空文字列） | `IsRecognitionFailed(result)`を呼ぶ | `true`を返す |

## セルフチェック（重複排除・不足確認）

### 重複排除の実施内容

- 3-1: 「レスポンス全体が空文字列」（TC-3-1-17）と「`null`文字列」（TC-3-1-18）は、いずれも構文エラー系だが検証入力が異なるため別ケースとして残しつつ、TC-18は種別を問わず「エラーになること」のみを検証する形にして、実装依存の分類差でテストが壊れないようにした。
- 3-1: めたんの観点にあった「`emotion`が7種以外→エラー」は、確認事項Lの決定により「エラーではなくフォールバック」に変わったため、異常系ではなくTC-3-1-14として設計し直し、異常系リストへの二重掲載はしていない。
- 3-3: `IsRecognitionFailed`と`IsTimedOut`は入力（`STTResult` vs `time.Time`×2）が完全に異なるため、境界値ケース同士で重複はない。

### めたんの観点との突合結果

| 観点（めたん） | 反映状況 |
|---|---|
| 3-1 7種全件個別ケース化 | TC-3-1-02〜08で反映 |
| 3-1 パース失敗の3種別（構文／スキーマ／値検証）の区別 | TC-3-1-24、TC-3-1-25で反映 |
| 3-1 `ValidateEmotion`（1-3）の再利用、二重管理の回避 | 対象関数の説明で明記。7種の判定基準そのものはTC-3-1-02〜08・TC-3-1-14で間接的に検証 |
| 3-1 Markdownコードブロック揺れの扱い | TC-3-1-20で「現状は構文エラーになる」ことを明示し、7章Qで責務の要確認を申し送り |
| 3-2 送出順序契約（確認事項M） | TC-3-2-01、TC-3-2-09〜12で反映 |
| 3-2 `error`発生後の後続イベント禁止契約 | TC-3-2-13で反映 |
| 3-2 `done`の重複送出・欠落禁止契約 | TC-3-2-14、TC-3-2-15で反映 |
| 3-2 LLM失敗時の即`error`（確認事項K） | TC-3-2-06で反映 |
| 3-2 TTS失敗時の部分的成功（確認事項N） | TC-3-2-07で反映 |
| 3-2 テスト用シンク（`EventSink`）によるモック検証 | 対象関数の説明で明記。実SSEストリームには依存しない設計を前提とした |
| 3-3 `IsRecognitionFailed`／`IsTimedOut`の完全独立 | 2関数として明確に分離して設計。シグネチャが互いの入力型に依存しないことで担保 |
| 3-3 信頼度閾値の等号非対称性（確認事項P） | TC-3-3-R05〜R07で反映 |
| 3-3 無音継続時間の等号非対称性（確認事項O） | TC-3-3-T03〜T05で反映 |
| 3-3 1-5の`Clock`インターフェース再利用 | `IsTimedOut`のシグネチャに`now`を引数として持たせることで、1-5の`IsExpired`と同一パターンを踏襲 |
| 3-3 困惑メッセージ・感情マッピングはスコープ外 | 本書冒頭で明示し、テストケースには含めていない |
| 3-3 無音検出（音声解析）自体はスコープ外 | `IsTimedOut`は時間比較のみを対象とすることを明記 |

### 抽出した不足ケース（初期観点になかったが追加したもの）

- TC-3-1-22: `emotion`が空文字列の場合も確認事項Lの「7種以外」に含め、困惑へのフォールバック対象とすることを明示（めたんは異常系として想定していたが、L決定により挙動が変わる境界的な入力として境界値に位置づけ直した）。
- TC-3-2-08: 3-1でパース済みのはずの不正な`emotion`値が防御的に紛れ込んだ場合の挙動を明示的にケース化（めたんは「そもそも到達しない設計になっているべき」と指摘していたため、到達した場合の防御的挙動を確認する形にした）。
- TC-3-2-15: 全フロー（正常・TTS失敗・LLM失敗）を横断して「必ず`done`または`error`で終端する」ことを確認する契約テスト。
