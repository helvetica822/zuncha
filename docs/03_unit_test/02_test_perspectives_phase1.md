## 1-1. conversationIDのULID形式バリデーション

**根拠**: F-HIST-01, F-HIST-04 / 画面設計書8章「conversationID（URLパラメータ）」

### 正常系

- 有効な26文字ULID（例: `01ARZ3NDEKTSV4RRFFQ69G5FAV`）で true を返す。
- 実際の採番関数（`oklog/ulid/v2`等）が生成したULIDを本バリデータに通すと必ず true になる（生成⇔検証の往復整合性）。

### 異常系

- 25文字（1文字不足）で false。
- 27文字（1文字超過）で false。
- Crockford Base32の許容文字集合外（`I`, `L`, `O`, `U`）を含む場合に false。これらは曖昧回避のため意図的に除外されている文字なので、単なる「英数字チェック」では検出漏れが起きやすい要注意ポイント。
- 空文字列で false。
- UUID形式（ハイフンあり36文字）など、別のID形式との混同パターンで false。

### 境界値

- ちょうど26文字・許容文字のみ → true。
- 25文字 / 27文字 → false（桁数境界の前後）。
- 許容文字の"隣接除外文字"を個別に検証する：`H`の次は`I`を飛ばして`J`、`K`の次は`L`を飛ばして`M`、`T`の次は`U`を飛ばして`V`。境界1文字だけ差し替えたテストケースを用意する。
- ULID仕様上、128bit値の最大値制約により先頭文字は本来`0`〜`7`のみが正当（26文字×5bit=130bit>128bitのため）。**【7章B確定】値域チェックは対象に含めない。** 先頭文字`8`以上（例: `ZZZZZZZZZZZZZZZZZZZZZZZZZZ`）でも文字種・桁数さえ満たせば true になることを、正規表現通りの挙動として明示的にテストケース化する。

### 例外系

- 前後に空白を含む文字列（例: `" 01ARZ...FAV "`）→ **【7章C確定】trimせず false**。正規化は行わず1-4の責務とは分離する。
- 小文字ULID（例: 全部小文字化したもの）→ **【7章C確定】false（正規化しない）**。Crockford Base32はデコード時に大小文字を区別しない仕様もあるが、本要件は`[0-9A-HJKMNP-TV-Z]`の大文字のみを正とし、完全一致のみ許容する。
- 全角文字・絵文字混入時 → false。

### 責務分離の指摘

- 「形式バリデーション」と「DBにレコードが存在するかの確認」（画面設計書: 不正ID/DB非存在どちらもS-01へリダイレクト）は別レイヤーの責務ですわ。画面遷移仕様上は同じ結果（リダイレクト）に見えるため、実装時に1つの関数へ混ぜたくなる誘惑がありますが、それをやるとフェーズ1で「モック不要」のはずのテストにDBモックが必要になってしまいます。**形式バリデーションは `IsValidULID(s string) bool` のような文字列→真偽値の純粋関数として独立させること**を強く推奨しますわ。
- 正規表現を使う場合はパッケージレベルで一度だけコンパイルし、関数内で毎回`regexp.MustCompile`しない設計になっているか確認が必要ですわ（テスト自体の速度にも影響しますし、複数回呼び出しても副作用がない状態を保証できているかという観点でもテスト容易性に直結しますの）。

## 1-2. first_textのルーン単位20文字カット処理

**根拠**: F-HIST-05 / DB設計書5.4

### 正常系

- 20文字以下のテキストはそのまま返す（例: `"こんにちは"`（5文字）→無変換）。
- ちょうど20文字のテキストはカットなしで全文返す（末尾文字も欠落しない）。
- 21文字以上のテキストは先頭20文字（ルーン単位）だけを返す。
- 日本語・絵文字・英数字が混在するテキストで、マルチバイト文字境界を壊さずに20文字カットできる（バイト単位カットでは文字化けが起きる典型ケースの確認）。

### 異常系

- 空文字列 `""` を渡した場合、空文字列を返す（nilポインタ参照や例外を発生させない）。
- サロゲートペア・結合絵文字（例: ZWJ結合の家族絵文字、肌色修飾子付き絵文字）を含む場合、「Unicodeコードポイント単位」でのカットが「見た目の1文字（書記素クラスタ）単位」とズレて、絵文字が分割・破損する可能性がある。DB設計書5.4のGoサンプル実装（`[]rune`変換）はこの制約を内包しているため、意図した仕様かどうかの確認が必要。

### 境界値

- 19文字 → カットなし。
- 20文字 → カットなし（ちょうど境界）。
- 21文字 → 20文字にカット（境界の直後）。
- 1文字のテキスト → 無変換で返す。
- 1000文字などの極端に長いテキスト → 確実に20文字にカットされる。

### 例外系

- **【7章A確定】「…」はDB格納値に含めない。** 生のルーン単位20文字カットのみを`first_text`に格納し、`…`はフロント表示専用の装飾としてSvelte側（フェーズ4）で付与する。よって1-2のテスト対象は「`…`を含まない生の20文字カット」のみでよく、画面設計書とDB設計書5.4の記述の食い違いは解消済み。
- 改行・タブ等の制御文字を含む発話が20文字カットの対象に含まれるか（サニタイズ前提かどうか）。
- 前後空白を含むテキストが渡された場合、trim後にカットするのか、trimせずカットするのか（1-4のtrim責務との境界線を明確にする必要あり）。

### 責務分離の指摘

- 純粋関数（`string -> string`）として設計し、`conversations`レコードの生成処理（INSERT）とは分離すること。フェーズ2（2-1）で初めてテストする設計にしてしまうと、フェーズ1の「モック不要」の利点を活かせませんわ。
- マジックナンバー`20`を関数内にハードコードせず、`TruncateFirstText(text string, maxRunes int) string`のように引数化するか、少なくとも名前付き定数`const FirstTextMaxRunes = 20`として定義すること。テストコード側もこの定数を参照できると、仕様変更時の保守性が上がりますわ。

## 1-3. role・emotionのアプリ層バリデーション

**根拠**: F-EMO-01 / DB設計書2.2, 5.5

### 正常系

- `role='user'`, `emotion=NULL` → valid。
- `role='assistant'`, `emotion=` 7種のいずれか（喜び・怒り・悲しみ・楽しい・照れ・困惑・ドヤ顔）→ valid。7種**全部**を個別のテストケースとして網羅する（1つでも漏れると本番で新規感情が弾かれるリスクに気づけない）。
- `role='assistant'`, `emotion=NULL` → 許容されるか要確認（要件は「assistantのみ使用」であり「assistantは必ず持つ」とは書いていない）。おそらく許容されるべきだが、明示的にテストケース化して仕様として固定する価値がある。

### 異常系

- `role='user'`, `emotion='喜び'`（本来NULLのはずなのに値がある）→ invalid。
- `role='assistant'`, `emotion='普通'`（7種にない値）→ invalid。
- `role='admin'`など、CHECK制約外のrole値 → invalid。
- `role=''`（空文字列）→ invalid。
- `emotion=' 喜び '`（前後空白付き）→ invalid（trimして許容するか、しないかは要確認だが、既定は非許容が妥当）。
- ローマ字表記のemotion（例: `'happy'`）→ invalid。

### 境界値

- 7種の感情ラベルをテーブル駆動で1件ずつ検証（1件目・7件目を含め全件）。
- 7種のいずれかと1文字違いの文字列（例: `'喜'`のみ、`'喜びだ'`のような部分一致）→ invalid（前方一致や部分一致で誤ってvalid判定されないことの確認）。
- roleの大文字小文字違い（例: `'User'`, `'ASSISTANT'`）→ invalid（完全一致のみ許容）。

### 例外系

- **role単体は妥当（'user'）・emotion単体も妥当（'喜び'）だが、組み合わせとして矛盾する状態**（`role='user'` かつ `emotion='喜び'`）→ これはDBのCHECK制約（role/emotionそれぞれの許容値チェック）だけでは検出できず、アプリ層バリデーションでのみ検出可能な核心ケース。DB設計書5.5が「アプリ層でのバリデーションを推奨。DBレベルのCHECK制約は任意」としている理由そのものであり、この機能の存在意義に直結するテストケースですわ。
- `emotion`が空文字列`""`とNULL（Go側なら`*string(nil)`または`sql.NullString{Valid: false}`）の扱いの違い。空文字列をNULLと同一視するか、invalidとして弾くかは実装上の重要な論点。
- role・emotion両方が不正な場合、バリデーション関数がどちらのエラーを返すか（最初の1件で止まるか、両方の不正を集約して返すか）は関数のエラー設計次第 → 仕様として明文化しておくべき。

### 責務分離の指摘

- 「role単体の妥当性」「emotion単体の妥当性（7種チェック）」「role×emotionの組み合わせ整合性」は本来3つの異なる責務ですわ。1つの巨大な関数に混ぜると、テスト名が「roleとemotionが両方正しいことを確認する」のような曖昧な名前になり、1テスト1振る舞いの原則（`.claude/rules/tdd-comprehensive.md`）に反しますの。
  - `ValidateRole(role string) error`
  - `ValidateEmotion(emotion *string) error`
  - `ValidateRoleEmotionConsistency(role string, emotion *string) error`
  のように分割することを提案しますわ。こうすれば「`role='user'`のとき`emotion`は必ずNULL」という組み合わせルールだけを独立してテストでき、将来8種目の感情が追加されても組み合わせテストには影響しませんの。
- 7種の感情ラベルはマジックストリングとして関数内に埋め込まず、パッケージレベルの定数（例: `var ValidEmotions = []string{"喜び", "怒り", ...}`）として定義し、テストコードからも同じ定数を参照できる設計が望ましいですわ。

## 1-4. 入力バリデーション（空文字・空白のみのtrim判定）

**根拠**: NF-SEC-01 / 画面設計書8章

### 正常系

- 通常のテキスト（例: `"こんにちは"`）→ valid（送信可能）。
- 前後に空白を含むが中身がある文字列（例: `" こんにちは "`）→ trim後は非空なのでvalid。

### 異常系

- 空文字列 `""` → invalid。
- 半角スペースのみ（`"   "`）→ invalid。
- タブ・改行のみ（`"\t\n"`）→ invalid。
- 全角スペースのみ（`"　　　"`）→ Go標準の`strings.TrimSpace`・JSの`String.prototype.trim()`はいずれもUnicode空白（全角スペース U+3000含む）を除去対象にしているため、仕様上invalidになるはずだが、画面設計書の文言は「スペース・タブ等」としか書いておらず全角スペースを明記していない → 実装依存の挙動に仕様を委ねてよいか確認推奨。

### 境界値

- 1文字のみの非空白文字（例: `"あ"`）→ valid。
- 1文字のみの空白文字（`" "`）→ invalid。
- 空白+非空白+空白の組み合わせ（`" a "`）→ trim後1文字残るのでvalid。
- 極端に長い空白文字列（1000文字のスペースのみ）→ invalid。

### 例外系

- 絵文字・記号のみのテキスト（例: `"😀"`のみ）→ trimでは除去されないため valid 扱いになる想定。これが意図通りかを明示的に確認・固定しておく。
- **【7章D確定】ゼロ幅スペース（U+200B）等の特殊空白文字対応は本フェーズでスコープ外。** 標準trim関数（Go: `strings.TrimSpace` / JS: `String.prototype.trim`）で除去される範囲のみを対応範囲とする。ゼロ幅スペースのみの入力は「valid（送信可能）」という現行仕様通りの挙動として確定し、既知の制限事項であることをテストコード上にコメントで明記する（対応漏れが将来の調査対象として再発見されないようにするため）。

### 責務分離の指摘

- 「trimして空かどうか」の判定ロジックは、Go側（バックエンドの入力検証）とSvelte側（送信ボタンの活性制御、フェーズ4の4-2）の**両方**で必要になる。実装をそれぞれ独立して書くと、判定基準（例えばゼロ幅スペースの扱い）が将来ズレるリスクがある。ロジックそのものの共有は言語が違うため難しいが、**テストケース（仕様）は両フェーズで共通化**し、同じ観点セットを使い回すことを提案しますわ。
- この関数は`string -> bool`の極めて単純な純粋関数であるべきで、モックも依存も不要。もしHTTPハンドラーの中に直接埋め込まれている設計であれば、真っ先に抽出すべき対象ですの。

## 1-5. GC判定ロジック（expires_at < NOW()）

**根拠**: F-HIST-07 / DB設計書5.2

### 設計上の前提（★7章E確定済み）

DB設計書5.2によれば、GCの実処理は`DELETE FROM conversations WHERE expires_at < NOW()`というSQL文そのものであり、これは「Postgresが評価するSQL述語」ですの。もしGo側に判定ロジックの実体が存在しない（SQLに丸投げ）なら、フェーズ1で「モック不要の純粋ロジック」としてテストできる対象が存在しないことになり、実質フェーズ2（DB接続）でしかテストできない、という懸念を提起していましたわ。

**【7章E確定】Go側に`IsExpired(expiresAt, now time.Time) bool`という純粋関数を実装する設計を採用し、1-5はフェーズ1に残すことが決定済み。** テスト計画書4節の「時刻・乱数に依存するテストは時刻注入（Clockインターフェース等）で決定的にする」方針と整合させ、下記の境界値テスト（ちょうどNOWの前後）を実現するための前提が整いましたの。以下のテスト観点はこの決定を前提に進めてよい。

### 正常系

- `expiresAt`が現在時刻より過去（例: NOW()の1日前）→ GC対象と判定（`IsExpired = true`）。
- `expiresAt`が現在時刻より未来（例: NOW()の1日後、まだ30日以内）→ GC対象外（`false`）。
- 複数件（期限切れ・未期限切れ混在）のリストから期限切れ分だけを抽出する関数として設計する場合、対象件数が正しくフィルタされる。

### 異常系

- `expiresAt`がゼロ値（`time.Time{}`、西暦1年）の場合、当然過去なのでGC対象と判定される点を明示的に確認（「未設定」を意図しない形でGC対象にしてしまわないか、という防御的な観点）。

### 境界値（★この機能の核心）

- `expiresAt == now`（完全一致）→ SQLの`<`（`<=`ではない）に忠実に、GC対象**外**（`false`）と判定されること。この等号非対称性を明示的にテストすることが最重要ですわ。ここを曖昧にすると「期限ちょうどの会話が消えるか消えないか」の仕様がテストで固定されません。
- `expiresAt`が`now`の1ナノ秒前 → GC対象（`true`）。
- `expiresAt`が`now`の1ナノ秒後 → GC対象外（`false`）。
- `started_at + 30日ちょうど = expires_at`となるシナリオ全体（生成カラムのロジックと組み合わせた場合）でも、上記の等号ケースと整合すること。

### 例外系

- **関数内部で`time.Now()`を直接呼んでいる実装だと、「ちょうど境界」のテストが原理的に書けない**（テスト実行タイミングでNOWが変動するため）。Clockインターフェース（`type Clock interface { Now() time.Time }`）で時刻を注入できる設計になっているか、最優先で確認すべきポイント。
- タイムゾーンが異なる`time.Time`同士（JSTとUTC）を比較しても、絶対時刻として正しく判定できること（`TIMESTAMPTZ`型を扱う以上、Go側の実装でタイムゾーンの取り違えが起きないかの確認）。

### 責務分離の指摘（最重要）

- 「GC判定ロジック」という名称が、実際には性質の異なる2つの責務を指している可能性がありますわ。
  1. 個々のレコードが期限切れかを判定する**純粋ロジック**（`IsExpired(expiresAt, now time.Time) bool`）
  2. 実際にDBから期限切れレコードを削除する**Repository層の処理**（`DELETE FROM ... WHERE ...`実行、フェーズ2の2-1と重複）
  フェーズ1で扱うべきは(1)のみ。**【7章E確定】(1)を`IsExpired`として独立実装する方針が確定したため、フェーズ1で「モック不要」のまま扱える。** 実際のDELETE文（フェーズ2の2-1）は、この判定ロジックと整合する形で実装すること。

## 6. 横断的な指摘事項（つむぎ・WhiteCUL確認事項）

実装着手前に解消しておかないと、テストケース自体がブレる論点を一覧化しますわ。**→ 全項目、つむぎにより仮決定済み。詳細は[7章](#7-つむぎによる仕様決定)を参照。**

| # | 対象機能 | 論点 | 影響 | 状態 |
|---|---------|------|------|------|
| A | 1-2 | `first_text`の`…`省略記号はDB格納値の一部か、フロント表示専用の装飾か（DB設計書5.4のサンプルと画面設計書の記述が食い違って見える） | 期待値が丸ごと変わるため最優先で確認 | ✅決定：DB非格納、フロント表示専用 |
| B | 1-1 | ULID先頭文字の値域制約（128bit上限による実質`0`〜`7`制約）を形式バリデーションでチェック対象に含めるか | 境界値テストの範囲が変わる | ✅決定：チェックしない |
| C | 1-1 | 小文字ULID・前後空白付きULIDの扱い（許容/非許容） | 異常系ケースの期待値が変わる | ✅決定：非許容、正規化しない |
| D | 1-4 | ゼロ幅スペース等「見た目は空白だが標準trimで除去されない文字」への対応要否（NF-SEC-01のスコープ判断） | 対応するなら追加実装・追加テストが必要 | ✅決定：スコープ外 |
| E | 1-5 | GC判定を Go側の純粋関数として実装するか、SQLのWHERE句のみに委ねるか | フェーズ1着手可否そのものに関わる | ✅決定：`IsExpired`をGo側に実装、フェーズ1に残す |

## 総括：責務分離に関する全体所見

現時点（2026-07-08）でGoの実装コードは未着手（`go.mod`すら存在しない）ため、以下は「これから書く実装への事前要求」として述べますわ。

5機能に共通する望ましい設計は次の通りですの。

1. **すべて`(入力) -> (真偽値 or エラー)`の純粋関数として切り出すこと。** DBアクセス・HTTPリクエスト処理・ファイルI/Oを一切含まない状態にする。
2. **時刻に依存する1-5のみ、Clockインターフェースで時刻を注入可能にすること。** これがないと境界値テスト（ちょうど境界）が書けませんの。
3. **マジックナンバー・マジックストリング（20文字、7種の感情ラベル等）は定数化し、テストコードと実装コードで同じ定数を参照できるようにすること。** 仕様変更時の保守性に直結しますわ。
4. **「単体の妥当性チェック」と「複数フィールド間の整合性チェック」は別関数に分離すること（特に1-3）。** 1テスト1振る舞いの原則を守るためですの。

これらが満たされていれば、フェーズ1は本当に「モック不要」で完結する設計になっていると判断できますわ。逆にどれか1つでも欠けていたら、その機能は実質的にフェーズ2以降の性質を帯びてしまうので、着手前にWhiteCULへ設計レビューを一声かけてほしいですの。

**2026-07-08追記**: 6章の確認事項A〜Eはつむぎの仮決定（[7章](#7-つむぎによる仕様決定)参照）により全て解消済みですわ。1-1〜1-5の該当箇所も確定版に更新済みなので、ひまりへのテストケース設計、このまま進めてもらって大丈夫ですの。

## 7. つむぎによる仕様決定

6章で提起された確認事項A〜Eについて、つむぎが2026-07-08時点で仮決定した内容を記録する。ひまりのテストケース設計は本決定を前提として進めてよい。

### A. first_textの「…」省略記号について

- **決定**: DB格納値には含めない。DB設計書5.4のGoサンプル通り、生のルーン単位20文字カットのみを`first_text`に格納する。
- 「…」はフロント表示専用の装飾とし、表示ロジック側（Svelte）で付与する。表示側の実装・テストはフェーズ4で扱う。
- **理由**: DB（`VARCHAR(20)`）とサンプル実装の対応を崩さないシンプルな設計を優先。UI装飾はUI層の責務として分離した方が責務分離の原則にも合う。
- **1-2への影響**: 1-2の期待値は「`…`を含まない生の20文字カット」のみを検証すればよい。「`…`を含むか」という論点自体が消滅する。

### B. ULID先頭文字の値域制約（実質0〜7）について

- **決定**: 値域チェックは対象に含めない。要件定義書の正規表現`[0-9A-HJKMNP-TV-Z]`通り、文字種・桁数のみを検証する。
- **理由**: 自前のULID生成器で採番する限り実害はなく、値域チェックまで実装するのはこのフェーズでは過剰（YAGNI）。
- **1-1への影響**: 「先頭文字`8`以上を許容するかどうか」の境界値ケースは不要。文字種・桁数の境界値検証のみに絞る。

### C. 小文字ULID・前後空白付きULIDの扱い

- **決定**: どちらも非許容（`false`）。正規化（小文字→大文字変換、trim）は行わず、完全一致のみ許容する。
- **理由**: URLパラメータとして受け取る値は厳密一致にする方がシンプルで安全。正規化処理を追加すると責務が増え、1-4のtrim責務との境界も曖昧になる。
- **1-1への影響**: 「小文字ULID」「前後空白付きULID」はいずれも異常系ケースとして`false`を期待値に確定する。

### D. ゼロ幅スペース等への対応

- **決定**: 本フェーズではスコープ外。標準のtrim関数（Go: `strings.TrimSpace` / JS: `String.prototype.trim`）で除去される範囲のみ対応する。
- **理由**: NF-SEC-01は一般的な入力バリデーションを指し、ゼロ幅スペースのような特殊文字対策までは要求していないと判断。既知の制限事項として文書に注記する。
- **1-4への影響**: ゼロ幅スペースのみの入力は「valid（送信可能）」という現行実装通りの挙動を仕様として確定し、既知の制限事項としてテストコード上にコメントで明記する（対応漏れの再発見を防ぐため）。

### E. GC判定ロジックの実装場所

- **決定**: Go側に`IsExpired(expiresAt, now time.Time) bool`という純粋関数を実装する設計を採用し、1-5はフェーズ1に残す。
- **理由**: テスト計画書（`01_test_plan.md` 4章）で明記した「時刻注入で決定的にする」方針と整合させるため、また境界値テスト（ちょうどNOWの前後）を実現するために必須。実際のDELETE文（フェーズ2の2-1）はこの判定ロジックと整合する形で実装する。
- **1-5への影響**: めたんが「総括」で述べた懸念（SQLのWHERE句のみに委ねる設計だとフェーズ1が成立しない）は解消され、1-5はフェーズ1の純粋関数テストとして予定通り実施する。
