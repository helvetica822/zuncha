## 1. 目的

zunchaはSTT（Whisper.cpp）・LLM・TTS（VOICEVOX）という外部サービス依存を多く抱えるプロジェクトである。
これらを区別せず一斉にテストしようとすると、依存関係の準備・モック設計・非決定性の排除が同時多発的に発生し、
着手順序を誤ると開発が停滞するリスクが高い。

本計画書は、**モックしやすい純粋ロジックから段階的にテストを構築する4フェーズ構成**を定義し、
各フェーズにおけるRed→Green→Refactorサイクルの回し方・体制・モック方針を明文化することで、
実装メンバーが迷わずTDDを進められる状態を作ることを目的とする。

---

## 2. スコープ

### 対象

- Go側: Repository層・Service層・アプリ層バリデーションロジックの単体テスト
- TypeScript/Svelte側: フロントエンドの状態管理・バリデーション・表示分岐ロジックの単体テスト
- 外部サービス（STT/LLM/TTS）との連携部分は、**モックを用いた単体テスト**として実施（実サービスへの結合テストは対象外）

### 対象外

- 非機能要件（後述「8. スコープ外事項」を参照）
- 結合テスト・E2Eテスト・負荷テスト（別計画にて実施）
- UI/UXの見た目（デザイントークンの数値検証はスナップショット/ビジュアルリグレッションの範疇とし、本計画では対象外）

## 4. テスト方針

### Go側（フェーズ1〜3の主にバックエンドロジック）

- **テーブル駆動テスト（Table Driven Test）** を基本形式とする。正常系・エッジケース・異常系を1つのテストケーススライスにまとめ、`t.Run(tt.name, ...)` でサブテストとして実行する。
- アサーションには **testify（`stretchr/testify`）** の `assert` / `require` を使用する。
  - 続行可能な検証は `assert`、以降の検証が無意味になる前提条件は `require` を使い分ける。
- Repository層のテストは `testify/suite` を用いてセットアップ／ティアダウンを共通化することを推奨する。
- 外部依存のモックには `testify/mock` を使用する。

### TypeScript/Svelte側（フェーズ4）

- テストランナーは **Vitest** を採用する（Vite/SvelteKitとの親和性、ESM対応を重視）。
- コンポーネントのテストには `@testing-library/svelte` を用い、実装の詳細ではなくユーザーから見た振る舞い（DOM・ロール）を検証する。
- ロジックのみを切り出せる部分（バリデーション関数、状態遷移ロジック）は、コンポーネントから独立した純粋関数としてユニットテストする。
- `localStorage` 等ブラウザAPIへの依存は `vi.stubGlobal` / jsdom環境でモックする。

### 共通方針

- 1テストケース1振る舞いの原則を徹底する（`.claude/rules/tdd-comprehensive.md` 準拠）。
- テスト名は「振る舞い」で記述する（例: `TestValidateConversationID_有効な26文字ULIDでtrueを返す`）。
- 時刻・乱数に依存するテスト（GC判定、ULID採番）は、時刻注入（Clockインターフェース等）やシード固定によって決定的にする。

## 5. モック方針

外部サービスごとに、単体テストレベルでモック化するか実接続で検証するかを以下の通り定める。

| 対象 | フェーズ | 単体テストでの扱い | 理由 |
|------|---------|-------------------|------|
| PostgreSQL | フェーズ2 | **テスト用DB（Dockerコンテナ）に実接続、またはRepositoryインターフェースをモック化**の併用。CASCADE削除やインデックス挙動を検証するテストは実DB接続を優先する | クエリの正しさ（CASCADE、順序保証）はモックでは検証しきれないため |
| Whisper.cpp（STT） | フェーズ3 | **モック化**（インターフェース越しにスタブを注入し、認識結果・失敗ケースを固定値で返す） | ローカル音声処理の実行はテスト実行速度・再現性を著しく損なうため |
| LLM（AI応答生成） | フェーズ3 | **モック化**（HTTPクライアントまたはインターフェースをモックし、任意のJSONレスポンスを返す） | 外部API呼び出しの非決定性・コスト・レート制限を排除するため |
| VOICEVOX（TTS） | フェーズ3 | **モック化**（ラッパー層のインターフェース `TTSClient` 等をモックし、音声バイナリ生成は対象外とする） | F-TTS-02のAPIラッパー設計により、ラッパーの入出力契約のみを単体テスト対象とする |
| SSE配信 | フェーズ3 | **モック化**（`http.ResponseWriter` やイベントチャネルをモックし、送出されるイベント種別・順序・ペイロードを検証） | 実ブラウザ接続なしにイベント送出ロジックのみを検証するため |
| localStorage | フェーズ4 | **モック化**（jsdom環境 + `vi.stubGlobal`） | ブラウザ環境依存を排除し高速に実行するため |

## 6. フェーズ進行順序

各フェーズは機能単位でRed→Green→Refactorサイクルを回しながら進行する。フェーズをまたいだ並行着手は行わず、
前フェーズの主要機能のテストが揃った時点で次フェーズに着手する（依存が少ないフェーズ1から積み上げることで、
後続フェーズのモック設計の手戻りを減らす狙い）。

```
フェーズ1（純粋ロジック）
  └─ 機能単位でRed→Green→Refactorを反復
     例: 1-1 ULIDバリデーション → 1-2 first_textカット → 1-3 role/emotion → 1-4 trim判定 → 1-5 GC判定
        ↓ フェーズ1完了
フェーズ2（DB連携ロジック）
  └─ 機能単位でRed→Green→Refactorを反復
     例: 2-1 POST /conversations → 2-2 履歴コンテキスト構築 → 2-3 GET /audio/{ulid}
        ↓ フェーズ2完了
フェーズ3（外部連携・イベント処理）
  └─ 機能単位でRed→Green→Refactorを反復
     例: 3-1 LLM JSONパース → 3-2 SSEイベント送出 → 3-3 STT失敗/タイムアウト判定
        ↓ フェーズ3完了
フェーズ4（フロントエンドロジック）
  └─ 機能単位でRed→Green→Refactorを反復
     例: 4-1 入力モード切替 → 4-2 送信ボタン活性制御 → 4-3 エラー表現出し分け
```

各機能について、以下のサイクルを1単位として扱う。

1. **RED**: ひまりが設計したテストケースをもとに、WhiteCULが失敗するテストコードを作成する
2. **GREEN**: テストをパスする最小限の実装を行う（実装担当は別途アサイン）
3. **REFACTOR**: めたん・そらのレビューを踏まえ、テストコード・実装コードの双方をリファクタリングする
4. フェーズ内の全機能が完了した時点で、そらがフェーズ全体のQAレビューを実施し、次フェーズへの移行可否を判断する

## 7. 体制

| 担当 | 役割 |
|------|------|
| めたん | テストアーキテクト（全体のテスト戦略・設計レビュー） |
| ひまり | テストケース設計（各機能のテスト観点抽出・ケース一覧作成） |
| WhiteCUL | 単体テスト仕様書・テストコード作成 |
| そら | QAレビュー（フェーズ完了時の品質確認） |
| つむぎ | 進行管理（フェーズ進行・スケジュール調整） |

---

## 8. スコープ外事項

以下の非機能要件は、本単体テスト計画の対象外とする。結合テスト・負荷テストフェーズにて別途扱う想定とする。

| ID | 内容 | 扱い |
|----|------|------|
| NF-SEC-02 | CORS設定（社内ドメインのみ許可） | 結合テストで検証 |
| NF-SCALE-01 | 同時接続数上限（最大10人） | 負荷テストで検証 |
| NF-SCALE-02 | 単一インスタンス動作 | 結合テストで検証 |
| NF-PERF-01 | VOICEVOX・STT同時処理時の過負荷耐性 | 負荷テストで検証 |

> 上記4項目は単体テストのRed/Green/Refactorサイクルには乗せず、本計画書のフェーズ1〜4完了後に別途「結合・負荷テスト計画書」を作成して対応する。
