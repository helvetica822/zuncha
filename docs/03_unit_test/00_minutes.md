## 議題 1: 単体テストフェーズの進め方（担当: つむぎ）

### 背景

zunchaはSTT（Whisper.cpp）・LLM・TTS（VOICEVOX）という外部サービス依存が多いプロジェクトであるため、
全機能を一斉にテスト着手すると依存関係やモック設計が輻輳し、開発が停滞するリスクが指摘された。

### 決定事項

#### 4フェーズ構成の採用

モックしやすい純粋ロジックから段階的にテストを進める方針で合意。

| フェーズ | 内容 | モック要否 |
|---------|------|-----------|
| フェーズ1 | 純粋ロジック・バリデーション | モック不要（最優先） |
| フェーズ2 | DB連携ロジック（Repository層） | テスト用DBまたはモック |
| フェーズ3 | 外部連携・イベント処理 | モック多用 |
| フェーズ4 | フロントエンドロジック | 一部モック（localStorage等） |

各フェーズの対象機能は以下の通り（詳細は `01_test_plan.md` を参照）。

- **フェーズ1**: conversationIDのULID形式バリデーション（26文字・Crockford Base32）、first_textのルーン単位20文字カット、role・emotionのアプリ層バリデーション、入力バリデーション（空文字・空白trim判定）、GC判定ロジック（`expires_at < NOW()`）
- **フェーズ2**: `POST /conversations`（ULID採番＋GC実行）、会話履歴コンテキスト構築（直近10往復／最大20メッセージ）、`GET /audio/{ulid}`（読込→fetched_at更新→ファイル削除→レコード削除の順序保証）
- **フェーズ3**: LLM応答JSONパース（text/emotion同時抽出）、SSEイベント送出ロジック、STT失敗判定・8秒無音タイムアウト判定
- **フェーズ4**: 入力モード切替とlocalStorage保存、送信ボタンの活性制御、エラー表現の出し分け（ずんだもん応答バブル vs トースト）

#### テスト方針

- Go側: **table driven test + testify** を採用。
- TS/Svelte側: **Vitest**（+ `@testing-library/svelte`）を採用。

#### モック方針

外部サービス（Whisper.cpp / LLM / VOICEVOX）は単体テストではすべてモック化し、実接続検証は結合テストに委ねる。
PostgreSQLはRepository層のクエリ挙動（CASCADE削除・順序保証等）を検証する必要があるため、テスト用DBへの実接続とモックを併用する。

#### 進行方式

フェーズをまたいだ並行着手はせず、フェーズ1から順に機能単位でRed→Green→Refactorサイクルを回す。
フェーズ完了時にそらがQAレビューを行い、次フェーズへの移行可否を判断する。

#### 体制

| 担当 | 役割 |
|------|------|
| めたん | テストアーキテクト |
| ひまり | テストケース設計 |
| WhiteCUL | 単体テスト仕様書・テストコード作成 |
| そら | QAレビュー |
| つむぎ | 進行管理 |

#### スコープ外の明確化

非機能要件（CORS設定、同時接続数上限、パフォーマンス）は単体テストの対象外とし、結合・負荷テストフェーズで別途扱うことを確認。

### 決定事項

| # | 論点 | 決定 | 理由（要約） |

| F | 2-1: ULID採番（INSERT）とGC実行（DELETE）のトランザクション境界 | **別トランザクション**とし、GCはbest-effortとして扱う。GC失敗時もログ記録のみで新規会話作成（INSERT）は必ず成功させる。処理順序はGC→INSERT | GCは副次的なクリーンアップ処理であり、ユーザーの主目的（新規会話作成）をGCの失敗で道連れにすべきではない。GCは冪等なので次回POST時のリトライで実害は小さい |
| G | 2-2: 並び替えの責務レイヤー、および「直近10往復」の解釈 | 並び替え（古い→新しい）は**Repository層で完結**させ、呼び出し元には常に時系列順で返す契約とする。「直近10往復」は単純な**「最大20件」の件数上限**として実装（往復ペア単位のカウントはしない） | 通常運用ではuser/assistantが交互に並ぶため実質的に等価であり、異常データ対応まで作り込むのは過剰（YAGNI）。並び替えをRepository層に閉じ込め呼び出し元の実装ミスを防ぐ |
| H | 2-3: fetched_at更新後のファイル削除失敗時の自動回復要否 | **自動回復バッチは実装しない**（スコープ外）。部分インデックスによる検出のみで十分 | 現行要件に自動回復機能の要求はなく、過剰実装を避ける。将来必要になれば別途対応 |
| I | 2-3: 「ファイル削除→レコード削除」vs「レコード削除→ファイル削除」の順序 | 現行のDB設計書5.3通り「**物理ファイル削除→レコード削除**」の順序を維持 | 設計書に明記された順序の変更は本テストフェーズの範囲を超える設計変更。リスク（孤立ファイル・幽霊レコード）はテストケースに明記する |
| J | 2-3: 同一ULIDへの同時多重リクエストの排他制御要否 | **排他制御は実装しない**（スコープ外）。二重リクエスト時の挙動は「未定義動作」として文書に明記するに留める | 要件定義に排他制御の要求はなく、過剰実装を避ける（YAGNI） |

## 議題 6: そらのQAレビュー指摘（⚠要修正）と修正対応

### そらのレビュー結果

判定: **⚠要修正**。フェーズ2テストコードに対し、以下の指摘があった。

#### 重要指摘: TC-2-1-11が原理的に成立しないテストになっている

`conversation_repository_test.go`のTC-2-1-11（`expires_atがちょうどNOW()のレコードはGC対象外`）が、正しく実装されたGCに対してほぼ確実に失敗する設計になっていた。

- **原因**: Go側で`started_at = time.Now() - 30日`としてINSERTしてから`repo.GC(ctx)`を呼ぶまでの間に必ず時間が経過するため、GC実行時にPostgres側が評価する`NOW()`は常に`expires_at`より後になる。結果として`expires_at < NOW()`は常に真となり、「ちょうど一致で削除されない」ことを期待するテストが、正しい実装であっても必ず失敗する。フレーキーではなく原理的な矛盾。
- **つむぎの決定**: `ConversationRepository.GC`のシグネチャに`now time.Time`を追加し、`GC(ctx context.Context, now time.Time) (int64, error)`として呼び出し元からGoで判定基準時刻を注入する設計に変更する。フェーズ1の1-5（`IsExpired(expiresAt, now time.Time) bool`）で確立したClock注入の思想と一貫させることで、境界値（`expires_at == now`）を確定的に検証できるようにする。

#### 軽微な指摘（2点）

| # | 対象 | 指摘内容 |
|---|------|---------|
| 1 | TC-2-2-13（同一ミリ秒の順序安定性） | 「2回取得して結果が一致する」だけでは不十分。返却順序がタイブレーカー（id等）に従っていることを直接アサートする形に見直すべき |
| 2 | TC-2-3-12（同時リクエスト） | `successCount==1`のアサーション自体は妥当だが、「排他制御なし＝未定義動作」（SQLの原子性に依拠する挙動であり、アプリの明示的ロックとは別）という整理をコード上のコメントに明記すべき |

### 修正対応（WhiteCUL）

- **`08_test_specification.md`**: 3.2節の`ConversationRepository`インターフェース定義を`GC(ctx context.Context, now time.Time) (int64, error)`に更新。シグネチャ変更の経緯を注記として追加。TC-2-1-11の記載をGo側`now`注入方式に合わせて更新。変更履歴に追記。
